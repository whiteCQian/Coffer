# Coffer 项目优化检查报告

检查日期：2026-10-26（Asia/Hong_Kong）。基线：`9784e06` 与检查开始时的未提交工作区。配套待办见[项目未完成事项排查](项目未完成事项排查.md)。

## 1. 结论与证据强度

现有架构已经考虑 owner 隔离、内容授权、持久操作意图、幂等、正文校验和恢复，不建议推倒重写。当前最值得投入的是**模式/状态一致性、数据库读取成本、轮询与首屏资源，以及可持续执行的测试门禁**。

本报告共列 13 项，分为三类：

- **代码确认**：静态调用链可以直接证明存在相应行为；没有声称全部经过真实部署复现。
- **本次实测**：本轮实际执行命令、构建或浏览器测试得到的结果。
- **风险/优化建议**：实现方式可能在一定规模下出问题，需要基准测试确认影响，不能直接写成已发生故障。

未执行当前 CVE/许可证在线审计和真实服务器渗透测试；不作“完全安全”或“已经存在严重漏洞”的结论。下列 P1/P2 是改进先后，不是漏洞评级。

## 2. 优先修正的行为问题

### O01 · P1 · 本地模式下的重新分析请求固定为 API【代码确认】

**证据**：[FilesView.vue](../frontend/src/views/FilesView.vue) 第 303、333 行；[FileDetailDrawer.vue](../frontend/src/components/FileDetailDrawer.vue) 第 176 行；[governance.ts](../frontend/src/api/governance.ts) 原样发送请求；[GovernancePreviewService.java](../backend/src/main/java/com/coffer/governance/application/GovernancePreviewService.java) 第 108、164 行；[ModelRuntimeModeService.java](../backend/src/main/java/com/coffer/model/runtime/ModelRuntimeModeService.java) 的 `resolveForTask`。

**触发与影响**：用户已启用并校验 LOCAL 模式，从这些入口创建分析/预览，前端仍传 `API`，后端因不匹配而拒绝。内容发送确认弹窗读取了实际目标，但没有修正请求体中的固定模式。不是“LOCAL 功能尚未实现”，而是入口没有正确接入。

**建议**：优先省略可选模式，由服务端解析当前有效模式；若需要显式参数，应与内容授权快照绑定，不能固定写死，也不能在失败后自动改用 API。

**验证**：LOCAL/API × 单文件/批量/预览；增加“授权后配置改变”回归，确保拒绝旧快照且不向错误目标发送内容。

### O02 · P1 · Web 上传进度没有统一到正式归档状态【代码确认】

**证据**：[webUploads.ts](../frontend/src/stores/webUploads.ts) 第 47–49、59–60 行；[WebUploadProgress.vue](../frontend/src/components/WebUploadProgress.vue) 第 11、30–44、63 行；[WebHomeView.vue](../frontend/src/views/WebHomeView.vue) 确实挂载该组件。

**触发与影响**：分析 `COMPLETED` 且没有待确认标签时，条目进入 `COMPLETED`，显示“已完成”，并可被“收起已完成”移除；这个判断不读取 `archived/taskState`。点击“采用建议标签”仅调用标签确认，并没有执行归档。`savedOnly` 又优先保持 `SAVED`，即使后来在其他入口已归档也可能显示旧阶段。

这不会单凭上述逻辑造成正文丢失，但会让同一文件在进度区、列表和操作记录呈现不同的完成含义，与已有“一次确认归档”流程脱节。

**建议**：统一从后端业务状态投影生成显示状态；如进度区仅描述上传/分析，应明确写“分析完成、待归档”。采用共用确认卡或直接承接归档动作，移除逐标签确认的重复流程。

**验证**：无标签、确认标签未归档、归档中/失败/成功、仅保存后归档、刷新恢复和文件被删除；同时检查任务计数和收起逻辑。

### O03 · P1 · 账号隔离回归夹具已过期，测试未纳入前端 CI【本次实测＋配置确认】

**证据**：[identity-isolation.mjs](../frontend/tests/identity-isolation.mjs) 没有 `/admin/embedding` 分支，未匹配接口返回 `[]`；[AdminEmbeddingPanel.vue](../frontend/src/components/AdminEmbeddingPanel.vue) 第 9–13 行把结果写入表单并计算 `trim()`；[ci.yml](../.github/workflows/ci.yml) 前端任务只安装依赖和构建。

**本次结果**：原脚本出现 `Cannot read properties of undefined (reading 'trim')`，堆栈定位到 `AdminEmbeddingPanel.vue`。在 `.test-tmp/project-review-20261026/` 的临时脚本中仅补齐该接口的有效空配置后，账号切换、迟到响应隔离、管理员私有 API 边界和会话过期测试通过。正式脚本未修复，不能记作原测试通过。

**建议**：修复正式夹具并提取共享 DTO 工厂；未知请求直接让测试失败，避免统一成功响应掩盖缺失接口。将相关浏览器回归加入 CI，优先覆盖账号切换、上传、LOCAL 模式、归档与手机操作。

**验证**：原文件直接运行通过；故意增加未处理 API 时，测试提供明确的缺失夹具错误，而不是后续页面空字段异常。这个发现不构成后端越权结论。

## 3. 性能与资源使用

### O04 · P1 · 文件列表的任务状态引入逐文件查询【代码确认；性能影响待量化】

**证据**：[FileService.java](../backend/src/main/java/com/coffer/file/application/FileService.java) 第 107 行逐项装配；[FileResponseAssembler.java](../backend/src/main/java/com/coffer/file/application/assembler/FileResponseAssembler.java) 第 34 行调用 `taskState.state`；[FileTaskState.java](../backend/src/main/java/com/coffer/file/application/FileTaskState.java) 第 14 行每次查询该文件最新归档操作。

标签已按整页批量读取，这是已有优化；但新状态投影又对每一行执行一次 Repository 查询。每页 N 个文件通常额外产生 N 次状态查询，叠加轮询后成本放大。尚未测量真实 SQL 次数与延迟，不声称已经造成慢请求。

**建议**：一次获取当前页 fileId 的最新归档操作，形成映射后纯内存投影状态；查询必须保留 owner 条件和 `createdAt + id` 的确定顺序。不要只取 archived 布尔值，否则会丢失撤销/冲突等状态。

**验证**：20/100 条页面的 SQL 数不再随条数线性增加；归档、失败、撤销中和撤销冲突状态与原实现一致。

### O05 · P1 · 首页总览先全量加载，再截取 50 条【代码确认；容量风险】

**证据**：[TaskOverviewService.java](../backend/src/main/java/com/coffer/task/application/TaskOverviewService.java) 第 48–53 行查询完整处理中/失败/待确认集合，之后第 56、66、78 行才 `limit(MAX_ITEMS)`。失败项过滤还逐个查文件及操作状态，装配时再次解析文件 ID。

**影响**：接口只返回 50 条，不代表数据库只读取 50 条。待处理/历史失败记录增长时，总览的查询次数、对象分配和内存压力仍会增长。它又被多个页面周期性刷新，属于比局部代码风格更值得优先处理的问题。

**建议**：把过滤与有效状态条件下推到数据库；用 count 查询计算真实总数，用有上限的查询取明细；批量装配文件/操作状态。若条件复杂，先明确统一投影语义，避免把“查前 50 条再过滤”做成计数不正确的新问题。

**验证**：按 1 千/1 万条虚构任务做基线，比较 SQL 数、峰值内存和 P95；计数与当前业务规则一致，明细仍按确定顺序返回。

### O06 · P2 · 文件页同时维护 5 秒和 10 秒两套轮询【代码确认】

**证据**：[FilesView.vue](../frontend/src/views/FilesView.vue) 第 385 行 `listTimer` 每 5 秒运行；第 426 行 `pollTimer` 每 10 秒运行。两者都调用 `loadList`，只有后一套检查 `document.hidden`。

**影响**：可见页面存在冗余调度机会；具体是否重叠发送受 loading 时序影响，不能简单断言请求固定翻倍。隐藏标签页仍可能由 5 秒计时器刷新；10 秒分支又没有归档中暂停条件，两套行为不一致。

**建议**：合并成一个生命周期明确的刷新器；隐藏页面暂停，恢复可见立即刷新；仅有活跃任务时使用短间隔，稳定态延长间隔或由操作事件触发。与共享 workspace 刷新统一去重。

**验证**：用请求计数检查可见/隐藏、离开页面、归档进行中、网络慢和失败重试，确保无堆积、无卸载后刷新。

### O07 · P1 · 搜索候选无数据库侧上限，词法任务没有自身等待截止时间【代码确认；负载风险】

**证据**：[HybridSearchService.java](../backend/src/main/java/com/coffer/service/HybridSearchService.java) 第 62 行词法任务使用默认 `CompletableFuture` 执行器，第 79 行 `await(lexical, 0)` 最终无超时等待，第 161 行才裁切 topK；[FileMetadataRepository.java](../backend/src/main/java/com/coffer/file/infrastructure/persistence/FileMetadataRepository.java) 的 FULLTEXT/LIKE 返回完整 `List`，标签候选也在服务层合并。

**影响**：高频词可能先加载大量候选再做融合；阻塞式数据库工作进入公共线程池，慢查询没有服务级总截止时间。已有 1500ms 左右向量等待边界不能约束词法路。这里没有证明死锁或生产超时，只确认应用层缺少相应限制。

**建议**：给词法和标签候选明确且可评估的上限、稳定相关性排序；使用有界专用执行器和数据库查询超时/总请求预算。H2 桌面可直接选择受支持的词法查询，避免每次先执行注定不支持的 MySQL 全文语法再捕获异常。保留已有无向量时的词法降级。

**验证**：常见短词、零命中、标签大量命中、数据库慢、向量故障与并发场景；比较召回质量、P95、候选数和线程/连接占用，避免仅为速度降低必要召回。

### O08 · P2 · 文件列表分页排序缺少唯一兜底字段【代码确认】

**证据**：[FileService.java](../backend/src/main/java/com/coffer/file/application/FileService.java) 第 121–124 行仅按上传时间、大小或名称排序；相比之下 Repository 的 `findRecentFiles` 已使用时间与 ID 组合。

**影响**：同名、相同大小或同一时间戳的数据没有确定的相对顺序。数据库在不同查询计划/分页之间可能重排同值记录；并非每次一定复现，但会增加重复/漏看风险。

**建议**：所有公开分页排序追加唯一 `id` 作为 tie-breaker。数据规模扩大后再评估游标分页，不必立即替换现有 Page API。

**验证**：准备至少两页同名/同大小/同时间数据，反复翻页检查顺序稳定和 ID 去重；并区分并发新增导致的 offset 位移，这不能只靠 tie-breaker 完全解决。

### O09 · P2 · 首屏资源较大，所有主要路由静态导入【本次实测＋代码确认】

**本次构建值**：主 JS **1,337.25 kB**，gzip **441.56 kB**；主 CSS **493.84 kB**，gzip **70.68 kB**。Vite 报告大于 500 kB 的 chunk 提示。数值来自本次生产构建，不是网络传输或页面交互耗时实测。

**证据**：[router/index.ts](../frontend/src/router/index.ts) 静态导入各页面；[main.ts](../frontend/src/main.ts) 全量注册 Element Plus 并导入整套样式；[vite.config.ts](../frontend/vite.config.ts) 没有专门分块策略。

**建议**：先将设置、管理员、治理和操作记录等非首屏页面改为路由懒加载，再评估组件按需引入和重复样式。按实际使用分析 vendor 分块；单纯调大警告阈值不会减小资源。

**验证**：同设备/网络下对比首屏下载、解析执行、LCP 和路由切换；桌面离线加载及部署后的缓存失效仍需正常。包体大小下降不自动等于体验改善。

### O11 · P2 · 模型综合校验重复探测，增加耗时与调用成本【代码确认】

**证据**：[SettingsView.vue](../frontend/src/views/SettingsView.vue) 的 `validateSelectedMode` 先并行执行各卡片 `testCard`，全部通过后调用 `validateRuntimeMode`；[ModelRuntimeModeService.java](../backend/src/main/java/com/coffer/model/runtime/ModelRuntimeModeService.java) 再调 provider 验证；[ModelRuntimeProviderFactory.java](../backend/src/main/java/com/coffer/model/runtime/ModelRuntimeProviderFactory.java) 第 69–75 行重新执行 Chat/Vision 检测，且顺序执行。

**影响**：常见成功流程中相同配置的 Chat/Vision 会被重复探测；网络慢时等待更长，也可能消耗额外额度。历史交付文档已经承认这一限制。

**验证**：统计一次综合测试的外部请求数；配置改变、结果过期、单项失败及并发修改时仍不能误启用模式。

### O12 · P2 · 上传降级把所有失败都解释成 AI 不可用【代码确认】

**证据**：[UploadZone.vue](../frontend/src/layout/UploadZone.vue) 第 53–60 行和 [FilesView.vue](../frontend/src/views/FilesView.vue) 上传逻辑均在通用 `catch` 中显示“AI 暂不可用或尚未授权”，再提供仅保存。

**影响**：网络断开、413、配额不足、会话异常、冲突或未知结果也可能进入该文案；用户会以为改用仅保存即可解决。重复使用幂等键已有帮助，但不能代替区分服务端到底有没有接收成功。

**建议**：按稳定业务错误码区分模型不可用、用户取消、未鉴权、文件限制、容量、冲突及未知上传结果；只有合适的错误提供仅保存降级，未知结果引导查询/重试同一操作；统一两个上传入口的处理。

**验证**：分别模拟 401/403/409/413、配额、超时、模型未就绪和取消授权；确认提示准确、不出现错误归因、不产生重复文件。

## 5. 暂不建议进行的大改

- 不因新旧 Java 包结构并存就全仓搬迁；优先在修改业务时增量拆分职责、补清晰命名和格式。
- 不把 JVM 内锁直接升级包装为多实例能力。当前不承诺共享库多主写，分布式锁/集群支持应作为另一个设计项目。
- 不为了速度省略 owner 约束、内容指纹、归档台账、授权快照或恢复流程。
- 不在没有实际审查结果时强制升级所有依赖或更换存储方案；先确认问题和兼容性。
- 不把本次经过模拟接口的浏览器测试称为真实 AI、MySQL/MinIO 或安装包端到端验收。

建议先做 O01–O05 与 O13，再合并 O06/O08 等低成本调整，随后基于性能基线推进 O07/O09/O11。O10 应随收尾同步建立，而不是等正式发布后再补。
