# AgentFS Nexus 已知问题与技术债务

> 盘点日期：2026-09-24；状态补记：2026-09-25。本文区分已有复现/记录的问题与从代码结构看出的风险。风险项需要通过真实环境或进一步设计确认；不把推测写成已复现 Bug。后续交付任务见[最终落地执行计划](./plans/AgentFS最终落地执行计划.md)。

## 1. 历史已解决问题与发布回归

### ISSUE-001：重新分析确认后的文件标签未可靠替换

- **状态：用户于 2026-09-25 确认已解决；原严重程度：高。**
- **现象证据：**问题手册记录真实 MySQL/API 操作中，预览只剩用户确认的新标签、归档批次和明细显示 `SUCCEEDED`，但文件详情仍返回原标签加新标签。记录的复现文件为 `file_id=8`。
- **根因线索：**旧运行 JAR 早于源码；现场仍运行旧增量标签逻辑。仅改源码而未重建并重启，问题仍会出现。
- **已有修复：**当前工作区的归档持久化逻辑先删除该文件全部标签关联，再写入确认集合，flush 后重新读取核验；不一致会抛错并回滚。删除改为原生 SQL。问题手册称 H2 回归已通过，启动脚本增加源文件或 `pom.xml` 新于 JAR 时拒绝启动的检查。
- **发布回归：**普通预览、重新分析、失败重试、幂等恢复及“标签不一致不能标成功”继续使用真实 MySQL + API + 页面验证；这是质量门禁，不再把 ISSUE-001 列为待修复缺陷。历史复现与关闭记录见[归档的问题手册](./archive/legacy/Cofferer待解决问题手册.md)。

## 2. 已确认的遗留实现与架构债务

### 2.0 存量数据完整性与部署暴露

- **P0，旧 MySQL 引用缺失**：盘点时 MySQL 有 7 条当前文件元数据，其中 ID 7、8 对应的 MinIO 正文对象在恢复副本中不存在。用户已确认整批旧单用户数据不迁移；切换时清理须在清理摘要中单独列出这 2 条，不能记成新系统迁移失败或自动补造正文。
- **P1，旧归档台账无法由当前对象验证**：14 条归档明细的 source/target 对象均在当前 MinIO 对象清单中缺失，包含 SUCCEEDED/SUCCEEDED 3 条、SUCCEEDED/NOT_REQUESTED 9 条和 SUCCEEDED/CONFLICTED 2 条。清理前保存其状态摘要；不得把旧 SUCCEEDED 当作正文仍存在的证明。
- **P1，MinIO 上游生命周期**：MinIO 官方仓库已于 2026-04-25 归档为只读。当前版本不适合作为新生产栈依赖；新架构用本地受控文件系统适配器，并从最终应用/镜像中移除 MinIO。旧数据只在切换前用于快照核验和获授权的整桶清理。[官方发布页](https://github.com/minio/minio/releases)
- **P1，MySQL 暴露所有网卡**：盘点时 Windows MySQL 服务的 3306 监听 0.0.0.0 与 ::。在服务器/NAS 生产部署中必须限制到私有容器网络或受信网段；公网只开放 HTTPS 反向代理。
- **对象保留风险**：97 个 MinIO 对象中约 92 个未被当前文件、归档路径和补偿表引用，是未引用候选而不是已确认垃圾。旧业务数据虽获用户授权在切换时清理，但必须使用显式目标/数量/摘要清单和可校验备份，不得直接清理 MinIO 内部 data 目录。
- **M0 快照**：MySQL 20 表/266 行逻辑备份已在隔离 schema 逐表恢复核验；119 个 MinIO 数据文件已全量复制并校验，隔离副本读取 97 个对象正文并计算 SHA-256。H2/Redis 快照也已保存；Redis 本次未独立启动恢复。详细证据见 [M0 盘点记录](./plans/M0-存量数据盘点与保护记录.md)。

### 2.1 旧标签确认事件可绕开正式治理闭环

`tag.application.event.TagConfirmedEventListener` 在标签确认事务提交后直接调用 `StorageArchiveService.archive`。`file.application.FileOperationService.changeCategory` 也调用该历史归档服务。该路径不会按正式流程建立治理预览、操作批次台账、统一撤销和持久补偿，可能形成“对象已移动但台账缺失”的状态。

代码交接、领域模型均要求后续移除或限制此旁路。历史 `StorageArchiveService` 外部调用失败主要写日志并吞掉异常，删除旧对象失败则留下对象副本；主治理流程已有独立台账/补偿能力，但旧路径并未统一到该可靠性机制。

### 2.2 生产环境尚未建立身份认证边界

验收文档把系统定义为单用户私人模式；当前 `pom.xml` 未引入 Spring Security，Controller 也未形成登录/授权层。`/api/settings/**` 可管理模型端点和密钥、文件 API 可操作数据；`/api/test/hello` 会发起模型调用并返回模型回复。CORS 仅限制浏览器跨域来源，不等于 API 身份认证。

因此当前形态应按本机/可信私网单用户应用理解，不具备共享或公开网络多用户部署边界。若要部署到不可信网络，需要先补认证、授权和接口访问策略。

### 2.3 模型调用可能保存或输出用户内容

- `agentfs.model-log.enabled` 默认开启；`ModelCallLogger` 会将截断后的用户输入、AI 回复、错误和用量写入 `model_call_log`。
- `application.yml` 中 LangChain4j Chat 配置启用了 `log-requests` / `log-responses`。
- `DeepSeekTestController` 将模型回复写入 info 日志；错误响应会包含异常信息。

这不是已确认的密钥泄露事件，但文件内容/用户问题可能包含敏感信息。需要明确日志脱敏、开关、保存期限和导出/删除策略，并在实际部署日志配置中检查请求/响应正文是否打印。

### 2.4 事务和对象存储一致性路径复杂

- MinIO 对象复制、SQL 更新、删除旧对象不是一个原子事务；主治理路径依赖台账和补偿任务恢复。
- 历史 `StorageArchiveService` 用 `@Lazy` 自注入跨过 Spring 代理，再以 `REQUIRES_NEW` 修复 AFTER_COMMIT 陈旧事务上下文问题，时序理解和回归维护成本较高。
- 历史服务注释把删除失败的旧对象副本交给“后台 GC”，但当前代码检索未发现对应的统一 MinIO 孤儿对象清理任务；需确认是否存在部署外运维流程并补齐责任边界。

### 2.5 数据库关联一致性依赖应用层

迁移脚本没有为主要领域关系创建外键；例如 `file_tag_mapping.file_id/tag_id`、预览项与批次、操作明细与批次/文件等由应用层维护。这样便于补偿/迁移，但删除顺序、孤儿记录和数据修复需要应用测试保证。后续如考虑增加外键，应先核对历史数据、级联删除语义和 MySQL/H2 一致性。

### 2.6 新旧包结构并存

新业务边界在 `file`、`tag`、`task`、`governance`、`inbox`；旧的顶层 `service`、`repository`、`controller`、`entity` 仍承载跨领域或历史类。`Code-Wiki.md` 明确建议增量迁移，避免一次性大搬迁。短期债务是职责边界不完全一致、需要逐类判断代码归属。

## 4. 明确范围限制（不是已复现 Bug）

- 当前运行代码仍缺少多人认证与 owner 隔离；最终范围已改为三种形态都支持多账号，但尚未实现。
- 第一版不承诺音频、视频、压缩包、电子表格、演示文稿分析，也没有页码级引用。
- Embedding、Hybrid Search 和收件箱扫描默认关闭，需要显式配置。
- 前端/后端与 Redis、MinIO、数据库的本地部署脚本仍有机器环境前置条件。
