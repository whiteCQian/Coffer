## ISSUE-001：重新分析确认后，文件旧标签未被最终标签集合替换

### 基本信息

- 状态：`已解决`（2026-09-25 用户确认；保留发布回归）
- 首次记录日期：2026-09-21
- 影响模块：C11 重新分析、C06 预览确认、C07 批量归档执行、首页文件标签展示
- 严重程度：高
- 数据风险：用户确认的标签与文件最终标签不一致，可能影响检索、分类判断和后续治理操作

### 用户期望

用户点击“重新分析”进入整理预览页面后，可以修改 AI 推荐的建议标签。点击“确认选中”或“全量确认”后，修改后的建议标签应成为该文件完整且唯一的最终标签集合。

例如：

- 文件原标签：`采购合同、设备采购、合同编号CG-2025-0830、违约责任、争议解决、合同、华兴科技、东方设备制造`
- 用户在重新分析预览中删除全部 AI 推荐标签，仅保留：`华兴合同`
- 正确结果：文件最终只关联 `华兴合同`
- 不允许的结果：保留原标签并追加 `华兴合同`

### 复现步骤

1. 在首页选择一个已有多个标签的文件。
2. 点击“重新分析”。
3. 等待 AI 生成整理预览。
4. 在建议标签输入框中删除原推荐标签，输入一个全新的标签。
5. 勾选该预览项。
6. 点击“确认选中”。
7. 等待系统提示归档操作完成。
8. 返回首页并刷新页面。
9. 查看该文件的标签。

### 实际表现

目前出现过两种异常：

1. 原有标签没有删除，新标签被追加到原有标签之后。
2. 用户修改后的标签完全没有生效，文件标签保持不变。

最近一次真实环境复现中，首页显示 9 个已确认标签，包括原有 8 个标签和新标签 `华兴合同`。

### 已确认的数据证据

2026-09-21 对本地 MySQL 真实业务数据进行只读检查，确认：

- 目标文件：`file_id=8`
- 文件版本：`revision=9`
- 已确认重新分析预览：`preview_id=25c33971-6b75-4657-a87a-10f74c15a300`
- 预览项状态：`CONFIRMED`
- 预览项保存的 `suggested_tags`：仅包含 `华兴合同`
- 对应归档批次：`archive-65346ee1-adc9-4e3e-9387-2cb47db70564`
- 归档批次状态：`SUCCEEDED`
- 归档明细状态：`SUCCEEDED / COMPLETED`
- 文件版本从 `8` 更新为 `9`
- 归档完成后，`file_tag_mapping` 仍存在 9 条 `CONFIRMED` 关联

以上证据说明：前端修改已进入预览数据，归档批次也被标记为成功，但正式文件的旧标签关联没有按预览中的最终标签集合被可靠替换。

### 已尝试但未完成真实验收的修复

1. 在预览页面点击确认时，自动保存所选项目中尚未保存的编辑内容，再调用确认接口。
2. 将归档落库语义从“追加标签”修改为“删除该文件原关联，再写入确认标签”。
3. 在归档幂等分支中同样执行标签同步，尝试修复旧版本已经提交元数据但未替换标签的情况。
4. 将 JPA 实体级 `deleteAll` 修改为按 `file_id` 执行数据库级批量删除。
5. 增加 H2 回归测试，覆盖普通预览、重新分析和已提交重试场景；自动化测试通过，但真实运行环境仍未验收成功。
6. 曾对 `file_id=8` 的历史脏数据执行一次定向清理，仅保留 `华兴合同`；用户后续反馈问题仍未解决，因此不能将该问题关闭。

### 当前判断

2026-09-25 用户确认重新分析后的正式标签集合问题已解决。本节以下内容是此前排查和复现的历史记录；原“关闭条件”中的场景继续纳入最终落地计划的发布回归，不再作为当前待修复缺陷。

2026-09-22 已通过真实 API 再次确认：预览 `2193e41d-084b-4c7d-9b99-c325451e3294`
的最终建议标签只有 `华兴科技`，归档批次
`archive-b6ddafce-45a7-4d3c-8d45-353dda80473a` 被标记为 `SUCCEEDED`，但文件
`file_id=8` 的详情接口仍返回 `采购合同、设备采购、华兴科技、华兴合同` 四个已确认标签。

同时确认运行脚本所使用的后端 JAR 最后构建于 2026-09-20，而包含整组标签替换修复的源码和
编译类更新于 2026-09-21。现场运行包陈旧是本次稳定复现的直接原因；仅统一项目目录和数据库，
但未重新打包并重启后端，仍会继续执行旧的增量标签逻辑。

当前源码已进一步加强为：使用原生数据库删除语句移除指定文件的全部关联、重新插入确认集合、
立即查询并校验最终标签集合；校验失败时事务回滚，归档明细不得标记为成功。启动脚本也增加了
“源码或 `pom.xml` 新于 JAR 时拒绝启动”的陈旧构建检查。H2 回归测试已经通过，新后端 JAR 已生成，
等待重启后按真实 MySQL 步骤完成最终验收。

重点怀疑方向：

1. 实际运行的后端进程并未加载当前工作区编译出的代码，仍在使用旧构建产物或其他目录中的项目副本。
2. 前端请求的后端地址与当前检查的数据库实例不一致。
3. 项目存在 H2 与 MySQL、多工作目录或多配置环境并存，导致修改、执行和检查落在不同数据源。
4. 归档任务完成后，还有其他异步流程重新写入旧标签关联。
5. 批量删除已执行但事务回滚，而归档台账状态仍被错误标记为成功。
6. 首页读取标签时使用了不同的数据源、缓存或重复数据聚合结果。

### 后续排查方案

后续集中处理时，应按以下顺序进行，不再仅依赖单元测试推断：

1. 关闭所有前端、后端和旧的 Java 进程。
2. 确认唯一项目目录、唯一后端构建产物和唯一启动命令。
3. 在启动日志中输出当前 Git 提交、工作目录、激活 Profile 和脱敏后的数据库地址。
4. 在预览更新接口记录 `previewId、itemId、fileId、suggestedTags`。
5. 在确认接口记录最终确认的预览项标签快照。
6. 在归档执行前后记录 `fileId` 的标签关联 ID 和标签名。
7. 开启事务 SQL 日志，确认是否实际执行 `DELETE FROM file_tag_mapping WHERE file_id = ?`。
8. 检查删除事务是否提交，以及是否有后续线程重新插入旧标签。
9. 归档批次只有在标签最终状态校验通过后才允许标记为 `SUCCEEDED`。
10. 使用真实 MySQL 和真实 API 完成端到端回归，而不仅使用 H2 服务层测试。

### 建议的防御性改进

- 在归档台账明细中保存确认时的标签快照，避免执行阶段重新读取可能变化的预览项。
- 标签替换后立即查询数据库校验最终集合；不一致时回滚事务并将归档明细标记为失败。
- 为归档完成状态增加不变量：正式文件标签集合必须与确认标签快照完全一致。
- 增加 MySQL Testcontainers 集成测试，覆盖删除旧标签、复用已有标签和事务回滚。
- 在前端归档完成提示中展示最终生效标签，避免只根据批次状态宣称成功。

### 关闭条件

必须同时满足以下条件才能标记为“已解决”：

1. 重新分析预览中只保留一个新标签后，首页刷新只显示该标签。
2. 数据库中该文件仅存在与确认标签集合一致的 `file_tag_mapping`。
3. 连续执行至少两次重新分析，第二次仍能完整替换第一次的标签。
4. 普通预览、重新分析、失败重试和幂等恢复四条路径均通过验证。
5. H2 自动化测试、MySQL 集成测试和真实页面端到端测试全部通过。
6. 归档台账不会在标签集合不一致时显示 `SUCCEEDED`。
