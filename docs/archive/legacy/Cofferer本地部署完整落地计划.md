# Cofferer Windows 本地部署完整落地计划

> **已废止的历史专项方案。** 本文基于旧的“Windows 本地库 + MinIO 镜像”设计；该设计已被[ADR-001](../../decisions/ADR-001-最终产品合同与存储架构.md)取代。最终交付改为三种形态共享受控的本地文件系统适配器，MinIO 不进入最终应用、发布包或部署栈。本文不再作为新功能或部署的验收依据。
>
> 文档状态：专项落地方案
>
> 适用版本：Cofferer 第一版，基于 C01～C16 已完成、C17～C20 待收尾的当前项目状态
>
> 目标：将当前依赖开发机环境的 Web 项目，落地为“Windows 本地文件库为主存储、MinIO 为镜像、Java 后端统一治理、Electron 负责桌面生命周期”的可验收本地节点。

## 1. 结论与范围

本地部署不是简单增加一个启动脚本，而是一次存储架构扩展。当前代码的上传、解析、预览、归档、撤销和文件读取都直接依赖 MinIO；而本地部署方案要求 Windows 本地文件库成为文件本体主存储，MinIO 只承担镜像和统一对象访问入口。

因此，本专项必须先完成存储抽象和本地文件生命周期，再实现 Electron 包装。不能先开发 Electron，再把现有 MinIO 逻辑强行包装进去。

本专项第一版目标：

- Windows 单机本地节点。
- 本地管理目录作为文件本体主存储。
- MinIO 作为本地文件库到对象存储的单向镜像。
- 复用现有文件解析、AI 分析、Dry-run、确认、归档、台账和撤销流程。
- 本地服务可以健康启动、重启恢复、失败补偿和安全停止。
- Web/NAS 的 MinIO 主存储模式保持原有行为。

第一版明确不包含：

- macOS 或 Linux 桌面安装包。
- 非空目录自动导入和历史文件迁移。
- Windows 节点与服务器/NAS 之间的双向正文同步。
- 跨设备正文自动合并。
- 直接修改 MinIO 内部 `data` 目录。
- Web 端直接修改文件正文。
- 复杂企业级 DLP、权限和多用户协作。

## 2. 当前项目基线与主要缺口

### 2.1 当前真实实现

- `FileUploadApplicationService` 上传时直接调用 `MinioStorageService.uploadFile`。
- `UploadPipelineService`、`FileParsingTool` 和治理预览流程通过 MinIO 读取文件内容。
- `ArchiveOperationService` 通过 MinIO 执行复制、删除、快照和撤销。
- `FileMetadata.storagePath` 当前实际保存的是 MinIO Object Key。
- `PathGenerator` 初始对象路径使用 `files/{日期}/{类型}/{UUID}_文件名`。
- `start-all.bat` 依赖本机 Java、MySQL、Redis、MinIO 和开发机绝对路径。
- 前端仍是 Vite Web 项目，没有 Electron 主进程、安装包或子进程管理能力。
- 收件箱扫描已经支持本地目录，但它只是“本地目录 → MinIO 上传”的导入入口，不是本地文件库主存储。

### 2.2 与本地部署方案的差距

现有代码缺少以下能力：

1. 本地文件库根目录配置、空目录校验和目录标识。
2. 本地相对路径与 MinIO Object Key 的统一约束。
3. 本地文件读写、复制、移动、删除和快照抽象。
4. 本地文件优先、MinIO 镜像异步补偿的状态机。
5. 本地文件修改后的版本、指纹和冲突检测。
6. 工作副本编辑和明确保存同步流程。
7. 本地服务的依赖发现、健康检查、启动顺序和进程归属管理。
8. Redis 在本地节点中的明确部署方案。
9. 本地模式与 Web/NAS 模式的自动化回归测试。

## 3. 总体架构决策

### 3.1 两个正交维度

部署形态和模型运行模式必须分开管理：

- 部署形态：`WEB_SERVER`、`NAS_SERVER`、`WINDOWS_LOCAL`。
- 模型运行模式：`API`、`LOCAL`。

例如，Windows 本地节点仍然可以选择 API 模型；本地部署不等于本地模型。无论部署形态如何，API 与 LOCAL 只能启用一种，任务需要记录执行时的模型模式快照。

### 3.2 存储抽象

新增统一存储端口，业务层不得继续直接依赖 `MinioStorageService`：

```text
FileStoragePort
├── MinioObjectStorage       Web/NAS：MinIO 是主存储
├── LocalFileStorage         Windows：本地管理目录是主存储
└── LocalMirrorCoordinator   Windows：本地文件库 → MinIO 镜像
```

统一端口至少提供：

- 写入文件流。
- 读取文件流。
- 获取文件大小和内容指纹。
- 判断文件是否存在。
- 复制或移动文件。
- 删除文件。
- 生成相对路径或对象 Key。
- 检查当前文件是否仍是预期版本。

业务层只处理逻辑路径，例如：

```text
contracts/2026/09/21/000-采购合同.txt
```

业务层不得保存或拼接 `D:\`、`C:\Users\` 等绝对路径。

### 3.3 Windows 本地数据目录

应用运行目录和用户文件库必须分离。建议使用以下结构：

```text
应用运行目录/
├── runtime/                 Java、Redis、MinIO 等运行组件
├── config/                  本机配置和加密主密钥
├── logs/                    后端、同步和启动日志
└── service-data/
    ├── h2/                  本地业务数据库
    ├── redis/               Redis 持久化数据
    └── minio/               MinIO 镜像对象数据

用户选择的本地文件库/
├── .cofferer-root           文件库标识和格式版本
├── inbox/                   受管控的待处理文件
├── managed/                 正式管理文件
├── work/                    工作副本
├── quarantine/              导入失败或待人工处理文件
└── lost-found/              发现数据库记录与本地文件不一致时的隔离区
```

数据库中只保存用户文件库的逻辑相对路径，不保存绝对路径。更换盘符或移动应用运行目录时，可以通过重新绑定根目录恢复使用。

### 3.4 一致性模型

Windows 本地模式采用“本地文件库先提交、MinIO 镜像最终一致”：

```text
本地文件写入成功
    → 数据库记录本地正式状态
    → 创建镜像同步任务
    → MinIO 镜像成功
    → 更新同步状态为 SYNCED
```

MinIO 镜像失败时：

- 不删除本地文件。
- 不回滚已经成功的本地文件提交。
- 文件仍可以在本地查看和继续治理。
- 数据库记录失败原因、尝试次数和下次重试时间。
- Web/NAS 端只看到同步成功的文件。

## 4. 文件生命周期设计

### 4.1 首次配置

1. Electron 或本地启动器启动后端。
2. 后端健康检查通过，但本地文件库未绑定时进入初始化页。
3. 用户选择目录。
4. 系统解析为绝对路径并校验：目录存在、可读写、为空或只包含系统允许的标识文件。
5. 系统创建 `.cofferer-root`、`inbox`、`managed`、`work`、`quarantine` 和 `lost-found`。
6. 将根目录绑定信息写入本机配置，不把绝对路径写入业务文件记录。

### 4.2 外部文件导入

```text
系统选择外部文件
    → 复制或移动到本地 inbox
    → 检查大小、修改时间和内容指纹是否稳定
    → 登记文件元数据
    → 从本地文件读取并解析
    → 生成 AI 整理建议
```

默认策略是“移动到管理库”，不保留外部位置的长期副本。移动前必须提示用户，并在失败时保留源文件。

### 4.3 Dry-run 与归档

Dry-run 只能写入预览表，不能移动本地正式文件，也不能写入 MinIO 镜像。

确认后的归档顺序：

1. 校验本地源文件仍存在。
2. 校验源文件版本、大小和内容指纹未发生变化。
3. 分配分类、日期和 `000`～`FFF` 序号。
4. 将本地文件原子移动到目标相对路径。
5. 更新数据库正式路径、版本和标签。
6. 创建 MinIO 镜像任务。
7. 镜像成功后更新同步状态。
8. 写入完整操作台账。

若数据库更新失败，应将本地目标文件恢复到源路径；若恢复失败，应进入 `lost-found` 并记录人工处理任务。

### 4.4 文件读取

Windows 本地模式优先从本地管理目录读取文件。浏览器仍通过后端 HTTP 接口获取文件流，Electron 不要求 Vue 渲染进程直接访问任意本地路径。

这样可以保持前端 API 不变，同时避免“为了桌面端访问而把完整文件暴露给前端脚本”。

### 4.5 工作副本编辑

工作副本编辑放在核心本地存储稳定之后实现：

1. 用户点击编辑，系统复制正式文件到 `work/{fileId}/{workCopyId}/`。
2. 记录编辑开始时的文件版本、大小、修改时间和 SHA-256。
3. 外部程序只修改工作副本。
4. 用户点击“保存并同步”时重新校验正式文件版本。
5. 若正式文件已经被其他流程修改，则拒绝覆盖并提示冲突。
6. 校验通过后将工作副本原子替换为新版本。
7. 更新本地文件版本、重新解析、重新生成标签和摘要。
8. 创建 MinIO 镜像更新任务。

第一版不允许 Web 端直接编辑正文；Web 端仍采用下载后重新上传的方式。

### 4.6 撤销和删除

撤销必须同时处理本地文件和镜像状态：

- 本地目标文件恢复到原始相对路径。
- 数据库恢复原始正式状态。
- 创建 MinIO 源路径镜像任务。
- 镜像成功后删除旧目标镜像。
- 若目标路径已被后续版本占用，转为冲突，不覆盖用户数据。

## 5. 数据模型与迁移计划

当前仓库已维护 Flyway V1～V14。建议从 V15 开始增加本地部署相关结构，具体字段名称可以在实现阶段按现有实体风格调整。

### 5.1 文件存储状态

在现有文件元数据基础上增加或拆分以下信息：

- `primary_storage`: `MINIO` 或 `LOCAL_FILESYSTEM`。
- `logical_path`: 文件的逻辑相对路径。
- `content_sha256`: 当前正式版本内容指纹。
- `local_revision`: 本地文件版本号。
- `mirror_status`: `NOT_REQUIRED`、`PENDING`、`SYNCED`、`FAILED`、`RETRYING`。
- `mirror_etag`: 最近一次镜像对象指纹。
- `mirror_attempts`。
- `mirror_last_error`。
- `mirror_next_attempt_at`。
- `mirror_updated_at`。

不把绝对路径作为业务字段持久化。

### 5.2 镜像同步任务

新增 `storage_sync_task` 或等价表，至少包含：

- 任务 ID。
- 文件 ID。
- 操作类型：`PUT`、`DELETE`、`REPLACE`。
- 逻辑路径。
- 期望内容指纹和大小。
- 当前状态：`PENDING`、`RUNNING`、`SUCCEEDED`、`FAILED`、`CANCELLED`。
- 尝试次数和最大尝试次数。
- 下次尝试时间。
- 最后错误码和错误信息。
- 创建、开始、完成时间。
- 幂等键。

同步任务必须使用唯一幂等键，防止应用重启后重复创建同一个镜像任务。

### 5.3 工作副本

如实现桌面编辑，新增 `file_work_copy` 或等价表，保存：

- 工作副本 ID。
- 文件 ID。
- 工作副本相对路径。
- 创建时正式版本。
- 创建时大小、修改时间和内容指纹。
- 当前状态：`OPEN`、`SAVED`、`DISCARDED`、`CONFLICTED`、`EXPIRED`。
- 创建者和时间。

### 5.4 建议迁移批次

- V15：增加存储后端、内容指纹和镜像状态字段。
- V16：增加镜像同步任务表及索引。
- V17：增加工作副本表和冲突状态字段。
- V18：增加本地部署绑定和运行状态记录，或明确由本地配置文件承载。

迁移必须同时维护 H2 和 MySQL 两套脚本，并增加迁移一致性测试。

## 6. 后端实施任务拆解

### C21：存储端口与本地文件存储

内容：

- 定义 `FileStoragePort`。
- 将 MinIO 能力改为适配器。
- 实现 `LocalFileStorage`。
- 增加根目录校验、路径规范化和路径穿越防护。
- 增加本地文件流、快照、复制、移动和删除能力。
- 将解析、预览、归档和撤销改为依赖端口。

完成标准：Web/NAS 模式回归测试不受影响；所有核心业务不再直接注入 MinIO 实现。

### C22：本地文件库初始化与导入

内容：

- 本地根目录选择和空目录校验。
- `.cofferer-root` 版本标识。
- `inbox`、`managed`、`work`、`quarantine`、`lost-found` 初始化。
- 外部文件移动、稳定性检测、失败恢复。
- 本地模式下的上传、解析和进度展示。

完成标准：外部文件进入本地管理库后，解析过程不依赖 MinIO。

### C23：本地归档与镜像同步

内容：

- 本地文件先提交，数据库登记正式状态。
- 镜像任务持久化和异步执行。
- 退避重试、应用重启恢复和任务幂等。
- MinIO 镜像失败提示。
- 镜像成功后更新远程可见状态。

完成标准：关闭 MinIO 后本地文件仍可查看；MinIO 恢复后任务自动补偿并最终达到 `SYNCED`。

### C24：本地模式治理、撤销和删除

内容：

- Dry-run 不写本地正式文件。
- 确认后的归档使用本地原子移动。
- 台账保存本地路径、镜像状态和版本信息。
- 单文件、批量撤销和失败重试适配本地存储。
- 清理历史旁路 `TagConfirmedEventListener -> StorageArchiveService.archive`，避免绕过治理链路。

完成标准：本地模式与 Web/NAS 模式共享治理规则，但使用各自的存储适配器。

### C25：工作副本、编辑和冲突

内容：

- 创建工作副本。
- 保存前版本校验。
- 保存后重新解析和重新生成预览。
- 保存同步到 MinIO。
- 冲突拒绝覆盖。

完成标准：正式文件不会被外部编辑程序直接修改；冲突时保留正式文件和工作副本。

### C26：本地运行时与 Electron

内容：

- 本地运行时目录初始化。
- Java 后端、Redis、MinIO 子进程启动。
- 端口检测和服务健康检查。
- 只停止本次会话创建的子进程。
- 异常退出后的残留进程处理。
- Electron 加载 Vue 前端并管理本地 API 地址。
- 首次启动向导和本地文件库绑定。

完成标准：用户不需要打开多个终端或手动配置开发机绝对路径即可运行。

## 7. 本地运行时方案

### 7.1 第一版推荐组件

本地节点建议包含：

- Java 运行时或随应用提供兼容 JRE。
- Spring Boot 后端。
- H2 文件数据库。
- Redis，用于会话记忆和可选向量索引。
- MinIO，用于镜像存储。
- Vue 前端资源。
- Electron 启动器。

MySQL 不作为 Windows 单机第一版的必需组件；Web/NAS 和服务器部署继续使用 MySQL。

### 7.2 服务启动顺序

```text
检查运行目录和配置
    → 启动 Redis
    → 等待 Redis 健康
    → 启动 MinIO
    → 等待 MinIO 健康并确认 bucket
    → 启动 Java 后端
    → 等待 /actuator/health = UP
    → 打开 Electron 窗口
```

任何组件失败时，启动器必须显示明确错误，不得打开一个看似可用但无法完成上传的前端页面。

### 7.3 配置与密钥

- 本地根目录、端口、服务路径通过本地配置文件或环境变量提供。
- `AGENTFS_SECRET_KEY` 随本机配置生成并提示用户备份。
- API Key 仍由后端 AES-GCM 加密存储。
- 日志不得输出 API Key、MinIO 密码、完整本地路径中的敏感文件名或文件正文。
- API 模式下显示数据可能离开本机的隐私提示。
- LOCAL 模式下显示当前本地模型端点，并禁止静默回退到云端。

## 8. API 与前端改造

建议新增或扩展以下接口，具体路径以现有 OpenAPI 约定为准：

- `GET /api/settings/deployment`：查询部署形态和本地存储状态。
- `POST /api/settings/deployment/local-root/validate`：校验目录是否可用。
- `POST /api/settings/deployment/local-root/initialize`：初始化本地文件库。
- `GET /api/local-storage/status`：查询文件库、MinIO 镜像和待补偿任务状态。
- `POST /api/local-storage/sync/{taskId}/retry`：重试镜像任务。
- `GET /api/files/{fileId}/content`：按部署形态返回本地或 MinIO 文件流。
- `POST /api/files/{fileId}/work-copy`：创建工作副本。
- `POST /api/files/{fileId}/work-copy/{workCopyId}/save`：保存并同步工作副本。
- `POST /api/files/{fileId}/work-copy/{workCopyId}/discard`：放弃工作副本。

前端必须显示：

- 当前部署形态。
- 本地文件库路径的脱敏展示。
- MinIO 镜像状态。
- 待同步数量。
- 最近一次同步错误。
- 工作副本冲突。
- API/LOCAL 模型运行模式和隐私说明。

## 9. 测试计划

### 9.1 单元测试

- 本地路径规范化和路径穿越防护。
- 空目录和非空目录判断。
- 相对路径到本地绝对路径的转换。
- 本地文件快照和 SHA-256 指纹。
- `000`～`FFF` 序号分配。
- 本地复制、移动和删除失败补偿。
- 镜像任务幂等键和重试退避。
- 工作副本版本冲突判断。

### 9.2 集成测试

- Windows 本地模式使用 H2、临时本地目录和真实 MinIO。
- 上传后本地文件存在，数据库保存相对路径。
- 解析阶段关闭 MinIO 仍可完成。
- 归档后本地路径与 MinIO Object Key 一致。
- MinIO 不可用时状态为 `PENDING` 或 `FAILED`，本地文件不丢失。
- MinIO 恢复后自动同步。
- 应用重启后未完成任务继续执行。
- 撤销后本地文件和镜像最终一致。
- 工作副本冲突不会覆盖正式文件。

### 9.3 回归测试

- Web/NAS 模式仍以 MinIO 为主存储。
- H2 与 MySQL Flyway 迁移版本一致。
- 现有 Dry-run、确认、归档、台账、撤销和引用来源测试全部通过。
- API/LOCAL 模式互斥规则不受部署模式影响。
- Redis 不可用时，系统按产品定义显示降级或阻止依赖会话记忆的功能。

### 9.4 手工验收

至少完成以下真实场景：

1. 选择非空目录，系统拒绝初始化。
2. 选择空目录，系统成功创建本地文件库。
3. 导入中文名文件，文件进入本地 `inbox`。
4. 文件分析、预览、确认和归档全部完成。
5. 归档后本地相对路径和 MinIO Key 一致。
6. 关闭 MinIO，继续查看和治理本地文件。
7. 恢复 MinIO，镜像任务自动补偿。
8. 重启应用，未完成任务不丢失。
9. 编辑工作副本时制造版本变化，系统正确报告冲突。
10. 执行撤销，不能覆盖后来产生的新版本。

## 10. 里程碑与建议顺序

### M0：方案冻结，1～2 个开发日

- 确定部署模式与模型模式分离。
- 确定本地文件库目录结构。
- 确定本地优先、MinIO 最终一致的原则。
- 确定 Redis 是否纳入本地运行时。
- 建立 V15～V18 迁移草案。

### M1：存储抽象，3～5 个开发日

- 完成 `FileStoragePort`。
- MinIO 适配器接入。
- 本地文件适配器完成。
- 解析和文件流读取迁移完成。

### M2：本地导入与治理，5～8 个开发日

- 本地根目录初始化。
- 本地 inbox 和正式文件库。
- 本地归档、撤销和删除。
- 路径与版本校验。

### M3：镜像同步与恢复，5～8 个开发日

- 同步任务表。
- 异步镜像。
- 失败重试。
- 重启恢复。
- 前端同步状态展示。

### M4：工作副本与冲突，5～8 个开发日

- 工作副本。
- 版本校验。
- 保存同步。
- 冲突处理。

### M5：本地启动器与 Electron，5～8 个开发日

- 本地运行时目录。
- Redis、MinIO、Java 子进程管理。
- 健康检查。
- 首次启动向导。
- Electron 打包。

### M6：集成验收与文档，5～10 个开发日

- 完成本地模式故障测试。
- 完成 Web/NAS 回归。
- 完成备份、恢复和迁移说明。
- 完成用户安装与故障排查文档。

整体预计需要 4～7 周，具体取决于是否在第一版同时实现工作副本编辑和 Electron 安装包。

## 11. 发布门禁

本地部署不能以“启动器能打开页面”作为完成标准，必须同时满足：

- 不依赖开发机绝对路径。
- 不要求用户手动启动多个服务。
- 空目录初始化和非空目录拒绝逻辑正确。
- 本地文件库成为文件本体主存储。
- MinIO 失败不会造成文件丢失。
- MinIO 恢复后任务可以自动补偿。
- 应用重启后状态和任务可恢复。
- 归档、撤销和冲突保护仍然有效。
- Web/NAS MinIO 模式没有回归。
- API Key、本地主密钥和文件内容不会进入日志或接口响应。
- 文档中的命令、目录和端口与实际发布包一致。

## 12. 最终建议

当前最先实施的不是 Electron，而是：

```text
存储抽象
  → 本地文件库主存储
  → 镜像同步与补偿
  → 本地治理和撤销
  → 本地模式集成测试
  → Electron 启动器
```

如果时间不足，优先保证前三项和故障测试；工作副本编辑与完整安装包可以作为第二阶段。但不能把“当前 start-all.bat 能启动 Web 页面”当作本地桌面部署已经完成。
