# Cofferer 第一版验收标准

> **历史基线，已被最终产品合同取代。** 本文保留 C01–C16 第一版历史范围；“单用户/无登录”及 MinIO 新部署权威存储不再适用于最终交付。请以[ADR-001](../../decisions/ADR-001-最终产品合同与存储架构.md)和[最终落地计划](../../plans/AgentFS最终落地执行计划.md)验收 Windows 桌面、服务器 Web 与飞牛 OS NAS。
>
> 本文固定 Cofferer 第一版的产品边界和验收口径，作为 C01 的唯一补充依据。
> 后续 C02～C20 可以细化实现，但不得改变本文已经确定的用户可见行为；如确需改变，必须先更新本文和任务清单。

## 1. 第一版范围

### 1.1 部署与用户边界

- 第一版是单用户、私人部署，不实现登录、注册、角色、权限、共享空间和多租户。
- 系统默认只有一个逻辑工作空间；所有文件、标签、预览计划和操作台账都属于该工作空间。
- 第一版支持本机部署，也允许部署到用户自己的 NAS 或服务器，但不承诺多实例并发写入同一工作空间。
- 第一版的权威数据源是数据库中的文件元数据、标签、任务和操作台账；MinIO 保存文件对象，Redis 只承担会话记忆和可选向量索引能力。

### 1.2 首批支持格式

首批支持以下文件格式：

- 文本和文档：`.txt`、`.pdf`、`.doc`、`.docx`
- 图片：`.jpg`、`.jpeg`、`.png`、`.gif`、`.webp`、`.bmp`

第一版不承诺音频、视频、压缩包、电子表格、演示文稿以及其他未列出的格式。未支持格式可以保存在存储中，但不得进入 AI 分析和自动归档流程，应明确显示为“不支持分析”。

### 1.3 第一版核心能力

第一版必须能够完成以下闭环：

```text
导入文件
  -> AI 分析
  -> 生成整理预览
  -> 用户查看、修改或跳过
  -> 用户确认
  -> 执行归档
  -> 查看操作台账
  -> 单文件或批量撤销
  -> 对话检索返回文件和引用片段
```

以下能力不属于第一版验收阻塞项：复杂规则引擎、完整 DLP/自动脱敏、音视频摘要、MCP Server、复杂跨平台实时监听、跨设备迁移，以及 MinIO/数据库/向量索引三方自动对账。

## 2. API 模式与本地模式

第一版只允许启用一种运行模式。模式在任务开始时记录快照，运行中的任务不因后续切换而改变。

### 2.1 API 模式

- Chat、Vision、Embedding 请求发送到用户配置的远程或局域网 API 兼容端点。
- 使用用户配置的 API Key；密钥只保存加密后的值，接口、日志和前端不得回显明文。
- 在设置页和涉及 AI 分析的操作页显示隐私提示：文件内容或解析文本可能发送到配置的模型端点。
- 未完成模型连通性校验时，不允许将模式切换为 API 模式或开始需要模型的任务。

### 2.2 本地模式

- Chat、Vision、Embedding 请求只发送到用户配置的本地模型端点，例如本机或用户私有网络内的 OpenAI 兼容服务。
- 不向公共云端点自动回退；本地端点不可用时任务失败并保留可重试状态。
- 页面明确说明：内容只会发送到用户配置的本地模型端点，但本地模型服务本身的日志和安全由用户负责。
- 本地模式不因缺少云端 API Key 而阻塞；是否需要鉴权由本地端点配置决定。

### 2.3 模式共同行为

- API 和本地模式使用相同的分析结果、预览、确认、执行、台账和撤销规则。
- 模式切换前必须验证目标模式所需的 Chat、Vision、Embedding 能力；不具备某项能力时，只禁止依赖该能力的任务，不得静默改用另一模式。
- 任务详情和操作台账记录实际使用的模式、模型标识和端点标识；不得保存 API Key 明文。

## 3. Dry-run 到撤销的固定流程

### 3.1 导入与分析

- 文件导入后先登记原始对象和文件元数据，再创建异步分析任务。
- 分析过程可以读取文件、解析文本、调用模型并生成建议，但不得改变正式归档路径、正式文件名、正式分类或已确认标签。
- 分析失败只影响当前文件；失败原因必须可见，并允许重试或重新生成预览。

### 3.2 Dry-run 预览

每个预览项至少展示：

- 原文件名和文件标识
- 建议文件名
- 建议分类
- 建议标签
- 建议摘要
- 预计归档路径
- 使用的运行模式和模型标识
- 当前预览状态、生成时间和过期时间

预览项支持用户修改建议、跳过单项、全量确认、部分确认和取消预览批次。

预览必须满足以下不污染条件：

- 不移动、复制、删除或覆盖正式文件对象。
- 不把建议分类、建议路径或建议名称写入正式治理字段。
- 不把建议标签标记为已确认。
- 预览取消或过期后不得被执行；需要重新分析才能生成新的可执行预览。

### 3.3 确认与执行

- 用户确认时创建一个操作批次，并为每个选中的预览项创建操作明细。
- 部分确认只执行被选中的项目，未选项目继续保留在原预览批次中或明确标记为跳过。
- 执行前记录原文件名、原分类、原路径和原文件对象标识。
- 执行时采用“新对象写入成功 → 数据库状态更新成功 → 旧对象清理”的顺序。
- 单个文件失败不得回滚或阻塞同一批次的其他文件；每条明细必须有独立结果和失败原因。
- 重复确认、重复执行同一操作幂等，不得产生重复对象、重复台账或重复撤销入口。

### 3.4 台账

每条已执行或失败的操作明细至少记录：

- 操作批次 ID、文件 ID、幂等键
- 原文件名、新文件名
- 原分类、新分类
- 原路径、新路径
- 操作来源、运行模式、模型标识
- 执行状态、撤销状态、失败原因
- 创建、开始、完成和撤销时间

台账是用户查看历史和执行撤销的依据，不使用前端状态或日志作为替代。

### 3.5 撤销

- 支持按单个文件撤销，也支持按操作批次撤销。
- 只撤销已成功执行且尚未撤销的明细；重复撤销必须幂等返回，不得再次移动对象。
- 撤销恢复原始路径、原始文件名和原始分类，并更新台账撤销状态。
- 撤销失败必须保留当前对象和数据库状态，记录失败原因并允许后续重试。

## 4. 冲突文件处理策略

第一版采用“检测即阻塞、绝不覆盖”的策略：

- 目标路径在预览生成时已存在，预览项标记为冲突，不允许直接确认执行。
- 执行阶段发生并发冲突时，同样标记为待处理，不覆盖目标对象，不删除源对象，不更新为已完成。
- 系统不自动生成 `(1)`、时间戳等新文件名，避免用户无法预知最终路径和撤销关系。
- 用户必须修改建议文件名、修改分类、选择跳过，或在确认冲突对象确实属于同一次幂等操作后重试。
- 撤销阶段发现原路径已存在且无法证明是本操作生成的对象时，进入撤销冲突待处理状态，不覆盖现有文件。
- 源对象不存在、目标对象不存在、文件已被再次修改或数据库记录缺失，都必须进入明确的异常/待处理状态，不能静默判定成功。

## 5. 验收场景

以下场景全部通过，才算 C01 定义的第一版核心边界被实现：

1. 上传一个支持格式文件，能够生成分析任务和整理预览，且预览期间正式路径、分类和标签不变。
2. 修改一条建议后部分确认，只有被确认项进入归档执行，未确认项不被移动。
3. 执行成功后能看到原路径、新路径、分类变化、批次和执行状态。
4. 同一确认请求重复提交，不产生重复归档对象或重复操作明细。
5. 单个文件执行失败时，同批次其他文件仍可完成，失败原因可查询和重试。
6. 目标路径冲突时系统不覆盖文件，该操作项进入待处理状态。
7. 对一个成功归档的文件执行撤销，文件恢复原路径和原分类。
8. 批量撤销时某一文件发生冲突，其他可撤销文件继续处理，冲突项单独保留待处理。
9. API 模式显示远程端点隐私提示，本地模式不向云端自动回退。
10. 对话检索返回真实存在的文件来源；文件失效时前端明确提示，而不是生成虚假来源。

## 6. 与后续任务的关系

- C01 只固定行为和验收口径，不实现数据库表、接口或页面。
- C02 已将本文的状态和异常规则转成[文件治理领域模型](./Cofferer文件治理领域模型.md)与状态流转。
- C03～C10 实现治理闭环；任何实现不得绕过本文的预览、确认、台账和冲突规则。
- C14～C17 实现运行模式、Provider、模型设置和敏感提示；模式语义以本文第 2 节为准。
