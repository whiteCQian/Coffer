# Cofferer C01～C16 开发交接文档

> **历史实现交接记录。** 本文总结第一版 C01～C16，不作为当前或最终产品合同；文中的单用户、MinIO 和 C17～C20 口径已由[ADR-001](../../decisions/ADR-001-最终产品合同与存储架构.md)、[需求追踪矩阵](../../plans/需求追踪矩阵.md)和[最终落地计划](../../plans/AgentFS最终落地执行计划.md)取代。

## 1. 文档目的

本文用于交接 Cofferer 第一版 C01～C16 的设计与实现成果，帮助后续开发者快速了解已经完成的功能、主要数据模型、接口边界和当前项目阶段。

本文只总结任务清单中的 C01～C16，不记录历史 Bug 修复过程，也不记录桌面端、本地文件库或其他本地部署方案。

## 2. 项目当前阶段

项目已经完成第一版核心治理闭环和模型运行模式基础能力，当前处于“核心功能完成，进入第一版收尾与质量验证阶段”。

已完成的任务阶段如下：

- **阶段 0：范围和架构准备**：C01、C02 已完成。
- **阶段 1：操作安全闭环**：C03～C10 已完成。
- **阶段 2：重新分析与检索可信度**：C11～C13 已完成。
- **阶段 3：模型运行模式**：C14～C16 已完成。

当前第一版核心流程已经具备：

```text
文件导入
  → 异步解析与 AI 分析
  → Dry-run 整理预览
  → 用户修改、跳过或确认
  → 批量归档执行
  → 操作台账查询
  → 单文件或批量撤销
  → 对话检索返回文件引用来源
```

任务清单中的下一阶段是 C17～C20：敏感文件识别、Docker Compose、集成与故障测试、项目文档完善。

## 3. C01～C16 完成情况

### C01. 固定第一版验收标准

**状态：已完成。**

**落地文档：**[Cofferer第一版验收标准](./Cofferer第一版验收标准.md)

已固定以下产品边界和验收口径：

- 单用户、私人模式。
- 首批支持 PDF、DOC、DOCX、TXT 和图片格式。
- AI 分类、标签、摘要和归档建议必须经过用户预览与确认。
- Dry-run 阶段不得污染正式文件数据。
- 确认后执行归档，并写入可查询、可撤销的操作台账。
- 单文件和批量撤销必须检测冲突，不能直接覆盖用户文件。
- API 模式与本地模型模式只能启用一种。
- 对话检索必须返回真实文件引用，不能由模型凭空生成来源。

### C02. 设计文件治理领域模型

**状态：已完成。**

**落地文档：**[Cofferer文件治理领域模型](./Cofferer文件治理领域模型.md)

已完成文件治理领域的状态和对象设计：

- 操作批次、操作明细和撤销状态。
- 文件生命周期状态、AI 分析状态、归档状态、操作状态和索引状态的分离。
- 操作幂等键、补偿任务和失败重试状态。
- 预览批次与预览明细和正式文件数据的隔离。
- H2 / MySQL 兼容的 Flyway 数据库升级方案。
- 确认、执行、失败、补偿、撤销和冲突处理的状态流转。

### C03. 新增操作台账数据表

**状态：已完成。**

主要成果：

- 新增 V8 操作台账数据库迁移。
- 新增 `ArchiveOperationBatch` 和 `ArchiveOperationItem` 实体。
- 新增批次和明细 Repository。
- 记录原文件名、新文件名、原分类、新分类、原路径、新路径。
- 记录操作来源、执行状态、撤销状态、失败原因和关键时间。
- 增加 H2 / MySQL 迁移契约测试和 H2 持久化约束测试。

台账是后续查询、撤销、幂等和补偿能力的事实依据，不能由前端状态或普通日志替代。

### C04. 实现批量导入基础能力

**状态：已完成。**

主要成果：

- 新增 `agentfs.import.inbox` 收件箱目录配置。
- 新增 V9 收件箱导入记录表。
- 使用周期扫描发现新增文件。
- 通过文件大小稳定性窗口，避免处理仍在复制中的文件。
- 使用 SHA-256 内容摘要进行重复导入判断。
- 支持失败退避重试和并发任务领取。
- 复用既有 MinIO 上传、解析和异步任务链路。
- 新增 `/api/inbox-imports/progress` 进度接口。
- 首页增加批量导入进度摘要展示。

第一版导入机制采用“配置目录 + 周期扫描”，不包含复杂实时文件监听。

### C05. 实现 Dry-run 分析预览

**状态：已完成。**

主要成果：

- 新增 `governance_preview_batch` 和 `governance_preview_item` 模型。
- 新增 V10 数据库迁移。
- 新增预览创建、查询和重新生成接口：
  - `POST /api/governance/previews`
  - `GET /api/governance/previews/{previewId}`
  - `POST /api/governance/previews/{previewId}/regenerate`
- 复用文本解析、图片识别、分类和标签生成能力。
- 预览中生成建议分类、标签、摘要、文件名和归档路径。
- 预览建议与正式元数据、正式标签和对象路径隔离。
- 保存 revision、ETag、大小和路径快照。
- 检测源对象变化和目标路径冲突。
- 支持预览失败、部分成功、过期、幂等重试和重新生成。

### C06. 实现预览确认接口和页面

**状态：已完成。**

主要成果：

- 新增预览项编辑接口：
  - `PATCH /api/governance/previews/{previewId}/items/{itemId}`
- 支持修改建议文件名、分类、摘要和标签。
- 支持逐项跳过、部分确认、全量确认和取消预览批次。
- 确认前重新校验文件版本、对象指纹和目标路径。
- 新增 `/governance/previews/:previewId` 页面。
- 页面展示原文件名、建议名称、分类、标签、摘要、预计路径、模型信息和错误原因。
- 文件列表支持多选并生成整理预览。

C06 只负责编辑和确认预览状态，正式对象归档及台账写入由 C07 负责。

### C07. 实现确认后的批量归档执行

**状态：已完成。**

主要成果：

- 用户确认后创建操作批次。
- 执行前保存文件原始状态快照。
- 调用对象存储归档能力完成对象迁移。
- 更新正式文件路径、分类和标签等元数据。
- 为每个文件写入独立的操作明细。
- 单文件失败与同批次其他文件隔离。
- 支持失败项重试。
- 前端展示批量执行结果和逐文件状态。

执行过程遵循“新对象成功写入、数据库状态更新、旧对象清理”的顺序，并保留失败状态供后续处理。

### C08. 实现操作台账查询

**状态：已完成。**

主要成果：

- 支持按操作批次分页查询。
- 支持按文件维度查询操作记录。
- 展示原路径、新路径、原分类、新分类和执行详情。
- 展示操作来源、时间、执行状态和撤销状态。
- 展示失败原因和补偿信息。
- 支持 JSON 和 CSV 导出。

### C09. 实现单文件和批量撤销

**状态：已完成。**

主要成果：

- 支持单文件撤销和按批次撤销。
- 按台账恢复原始路径、文件名和分类。
- 执行版本、对象指纹和文件存在性校验。
- 原路径已被占用时进入冲突状态，不直接覆盖现有文件。
- 处理对象不存在、文件被删除和文件再次修改等异常情况。
- 重复撤销请求具备幂等保护。
- 台账页面提供撤销入口和撤销状态展示。

### C10. 增加操作幂等和异常补偿

**状态：已完成。**

主要成果：

- 确认、执行和撤销均具备重复请求保护。
- 新增持久化补偿任务。
- 对象复制失败与数据库更新失败隔离记录。
- 支持旧对象清理重试。
- 支持定时补偿任务。
- 支持服务启动后的未完成任务恢复扫描。
- 台账页面支持查看补偿状态和手动重试。

这一阶段完成后，系统具备了“单条失败不阻塞批次、服务中断后可恢复、重复操作不重复产生结果”的基础可靠性。

### C15. 实现 API / 本地模式互斥配置

**状态：已完成。**

主要成果：

- 本地模式不可静默回退到 API 模式。

这里的 API / 本地模式指 AI 模型请求目标端点，不改变归档、预览、台账和撤销等业务流程。

## 4. 当前系统能力边界

目前系统已经能够完成以下核心场景：

1. 文件进入系统并创建异步处理任务。
2. 系统解析文件并生成分类、标签、摘要和归档建议。
3. 用户在预览页面检查并修改建议。
4. 用户部分或全部确认后执行归档。
5. 系统记录操作批次和逐文件台账。
6. 用户查询历史操作并导出记录。
7. 用户对成功操作执行单文件或批量撤销。
8. 系统对重复请求、对象变化和部分失败进行状态化处理。
9. 用户通过自然语言检索获得文件级引用来源。
10. 用户在 API / 本地 AI 模式之间进行互斥配置和模型连通性测试。

## 5. 关键交接信息

### 5.1 数据库迁移

当前 C03～C05 已使用 Flyway 增加治理相关结构：

- V8：操作批次和操作明细。
- V9：收件箱导入记录。
- V10：治理预览批次和预览明细。
- V11：治理补偿任务。
- V12：全局模型运行模式。
- V13：API / 本地模式的模型运行端点配置。
- V14：归档对象名称保留和并发分配锁。

H2 用于开发和测试，MySQL 用于生产环境，迁移结构需要保持兼容。

### 5.2 主要领域对象

- `ArchiveOperationBatch`：一次确认后归档操作的批次。
- `ArchiveOperationItem`：批次内单个文件的执行明细。
- 治理预览批次：一次 Dry-run 分析的容器。
- 治理预览明细：单文件的分类、标签、摘要、名称和路径建议。
- 收件箱导入记录：批量导入的来源、去重、稳定性和处理状态。
- 补偿任务：对象存储、数据库更新、旧对象清理等异常动作的后续执行记录。

### 5.3 后续开发注意事项

- 不要绕过“预览 → 确认 → 执行 → 台账 → 撤销”的治理链路直接修改正式数据。
- 新增状态时需要同时考虑幂等、重试、服务重启恢复和撤销影响。
- 预览建议与正式文件元数据必须继续隔离。
- 对话引用必须来源于真实检索结果，不能只依赖模型输出文本。
- 模型接入业务应继续依赖 Provider 抽象，不要在业务层直接调用具体模型 SDK。
- API Key 等敏感配置不得出现在日志、接口响应或前端明文展示中。
- 当前代码仍保留历史 `TagConfirmedEventListener -> StorageArchiveService.archive` 旁路；该路径可能绕过治理预览和操作台账，后续收尾时必须移除或限制，不能作为新的治理流程继续扩展。
