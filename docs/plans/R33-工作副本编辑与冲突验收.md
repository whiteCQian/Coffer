# R33 工作副本编辑与冲突验收

日期：2026-10-09。依赖 R31、R32；复用原有 `WorkSaveApplicationService`、保存意图、恢复、冲突另存及分析事件，没有另造正式文件替换 API。

## 实现与用户流程

文件详情与操作台账新增本地工作副本面板，仅 desktop 开启。创建时先登记数据库意图，再复制到当前 owner 的 `work/<UUID>/edit.<扩展名>`；目标不存在才能发布，沿用同目录 staging、大小/SHA-256 校验、fsync 和安全提交。每个副本有独立目录，未完成副本不会被正式对象扫描或 staging 回收清理。

“打开副本”先展示实际路径并确认，然后由系统文件关联打开；只能传入服务端根据 owner/UUID 派生且没有链接或 junction 的 work 文件，不能指定原件路径、应用命令或任意目录。允许普通文档和不含宏的 Office 格式，拒绝可执行文件和宏文档格式。Windows 桌面入口开启 AWT 打开能力；文件关联失败进入可见的 `APP_OPEN_FAILED`，磁盘副本保留。

关联打开可能复用现有 Office 进程，因此返回成功只表示打开请求已提交，不代表文档已关闭，也不以某个启动 PID 的结束推断编辑完成。用户先在外部应用保存到副本并关闭文档，再提交新版本。Office/LibreOffice owner 文件以及实际文件锁会阻止保存和清理；Word 截短文件名的 `~$` 标记也在独立副本目录内检测。崩溃遗留标记不会自动删除：确认应用退出后需核对该副本目录，或重新通过外部应用处理锁状态。

保存比较正式文件的 revision、SHA-256、大小、完整 mtime 和文件身份；Windows NIO 不提供 fileKey 时使用创建时间作附加身份判别。检查同时发生在提交前和保存意图提交事务中。副本读句柄持有只读锁并检查读取期间的大小、mtime 和身份；写入新正式对象先核对 SHA-256。正式文件通过原保存事务切换到新 key，revision 加一，发布既有分析事件并清除旧索引状态，由既有管道重新分析/建索引；旧正文进入持久化延迟清理。一个工作副本提交一个正式版本，继续编辑从该新版本再创建副本。

冲突保留原件与磁盘副本。另存沿用保存意图和 `restoreAsNewFile`，增加持久化 `preserve_only`：即使复制后立即强杀，恢复也只登记独立文件，不能更新原件。另存文件先显示“等待手动重新分析”，不会绕过模型目标和敏感内容授权。原件缺失时仍可另存已有副本。

关闭对话框提供保存后关闭、另存、保留、核对无未提交修改后关闭、放弃。关闭和放弃必须核对用户当前看到的 SHA-256；内容再次变化则拒绝清理。删除步骤有 `CLOSING`/`DISCARDING` 持久化意图并在启动时对账，失败保留副本和错误状态。已经提交的基线从保存意图读取，不会因“保留”或“记录异常退出”误判为未提交内容。

外部应用异常/未保存退出可显式登记 `APP_EXIT_UNCONFIRMED`。后端退出时未关闭的副本在启动后显示 `BACKEND_EXIT_UNCONFIRMED`；已提交或已另存的意图会恢复正确结果。界面明确说明只能恢复写到磁盘的内容，Office 内存中未保存的编辑需查 Office 恢复面板，不能显示成已经保存。

## 验证证据

- `DesktopWorkCopyIntegrationTest`：8 个真实 H2/本地文件场景，包括只传 work 路径、打开失败、发布新版本/分析事件、跨 owner 不可见、Office owner 文件与排他锁、revision/正文/大小/mtime/身份变化、提交前最后一次身份复查、原件缺失后的另存、未保存关闭选择、摘要确认变化和重启保留。
- 完整后端 `verify`：446 项，0 失败，0 错误，9 跳过。7 项真实 MinIO 合同本轮未启用，2 项符号链接用例受 Windows 权限限制；真实 junction、跨盘、ACL 与打包解析子进程已执行。
- `scripts/verify-work-copy.ps1`：9 个独立 JVM `halt(73)` /新 JVM 恢复边界。原保存链路的登记、发布、正文记账、DB 提交四处；新工作副本的打开、复制未就绪、另存复制未记账、放弃意图、保存已提交未更新副本台账五处。正文与台账核对通过。
- `scripts/verify-work-copy-ui.cjs`：无头 Edge 隔离 API 夹具验证路径确认/取消、应用异常、保留、模型授权、冲突可见、另存、确认 SHA-256 后放弃、刷新页面后的中断与占用状态；没有访问真实账号或正文。
- OpenAPI `WorkCopyView` 从隔离 dev 实例生成。桌面路由保持 desktop 限定，生产/桌面的 OpenAPI 入口继续关闭。前端类型检查和 Vite 生产构建通过。
- `scripts/verify-work-copy-office.ps1` 的真实 Word 验证通过，输出 `R33_OFFICE_PASS`：有效 DOCX 在自己的隐藏 Word COM 实例打开，磁盘保存后占用时拒绝提交；加入仅在内存中的修改并强杀该实例，磁盘副本只含上次保存内容，Coffer 显示异常退出且原件不变；确认测试 Word 已结束、核对并清理测试目录的隐藏残留 owner 文件后，新版本提交和关闭通过。脚本开始时拒绝与已有 Word 会话混用，只结束已证明属于测试的新进程，没有接管用户文档。该结果验证本机 Word，不替代其他 Office 版本/干净机安装验收。

## 重跑

```powershell
scripts/verify-work-copy.ps1 -MavenPath <mvn.cmd> -JavaPath <java.exe> -KeepArtifacts
scripts/verify-work-copy-office.ps1 -MavenPath <mvn.cmd> -JavaPath <java.exe>
```

UI 脚本使用 `COFFER_UI_ORIGIN` 指向隔离 Vite 或生产预览，`COFFER_PLAYWRIGHT_MODULE` 可指定现有 Playwright 模块。API 响应全部由脚本拦截。生产运行不依赖这些测试脚本或 Vite。
