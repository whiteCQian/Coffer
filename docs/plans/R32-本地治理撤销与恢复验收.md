# R32｜本地治理、撤销与恢复

实现日期：2026-10-08。共享的 GovernancePreviewService、ArchiveOperationService、ArchiveRollbackService、补偿状态机与删除任务直接使用桌面 FileStoragePort，不新增另一套本地业务规则。真实文件 H2、本地正文及 owner 目录继续沿用 R30/R31。

## 执行和最后清理来源

- 整理预览通过鉴权读取真实文件、保存建议和源 revision/指纹，不移动正文，不修改正式名称、位置、摘要、分类或标签。只有用户确认后才建立归档操作台账。
- 归档台账先保存完整 before/after 快照和固定目标；本地适配器在目标目录复制到同卷 staging，检查大小与 SHA-256、force 后采用 no-overwrite 的原子发布方式提交，不覆盖占用路径。
- 已校验的目标提交后，短数据库事务应用正式字段与完整确认标签集合。清理旧来源前重新核对正式快照、contentSha256/etag 和目标正文，再执行带摘要条件的删除；来源清理是最后的外部 I/O 步骤。
- 撤销沿用对应逆序：登记请求、确认当前归档状态、复制并校验原路径、持久化 rollbackCopyVerified、恢复完整原快照及新 revision，核对恢复后的正式字段与正文，最后清理旧归档正文。
- 占用的原路径/目标路径不因正文碰巧相同就被认领或覆盖。路径冲突保留双方，记录 CONFLICTED。副本已产生但 durable marker 尚未保存的中断点也按这个原则处理。
- 同 owner/file 的归档执行、撤销执行和补偿清理由共享的有界重入锁串行执行，避免恢复与用户重试在同一进程交错提交或清理。跨文件哈希碰撞只会增加等待，不改变 owner 授权。

## 过期补偿保护

原补偿路径只检查保留正文的 SHA-256，可能在正式元数据已被撤销或再次治理后继续清理旧路径。本轮在 DELETE_ARCHIVE_SOURCE 前调用 verifyArchivedFacts，在 DELETE_ROLLBACK_TARGET 前调用 verifyRestoredFacts；验证不通过时保留正文并进入补偿 MANUAL_REVIEW。

归档/撤销的正常执行和元数据已提交后的恢复路径也执行相同核验。旧台账没有完整快照时，归档来源清理至少必须符合已提交的文件身份、目标路径、名称、分类、revision 与摘要，不能无条件略过。完整快照继续校验正式字段及标签。

RESUME_ARCHIVE / RESUME_ROLLBACK 遇到 CONFLICTED、不可恢复或跳过结果时不再把补偿任务记成 SUCCEEDED，而是保留明确的人工处理态；一般 I/O 故障仍遵守已有退避与次数上限。历史已成功的归档/撤销不会因过期补偿重放被改写成失败。

归档清理发现来源已经不存在时，只有当前正式状态和保留目标已校验才能按幂等完成处理。不会重新查找或删除另一条路径代替缺失来源。

旧台账缺少 sourceSha256 时，正常归档清理使用已经复制、校验并提交的目标摘要作为条件，不临时计算待删除来源的新摘要来认领后来变化的内容；缺少足够身份的补偿任务仍需人工核对。

## 启动恢复与失败状态

启动时按有效普通用户核对中断操作，恢复持久化补偿工作，并立即执行一批有界待处理任务；后续仍由调度器按退避时间重试。不会因重复重启重置 FAILED/MANUAL_REVIEW 的次数或绕过已有 nextAttemptAt。

确定的步骤恢复到完整正式状态；无法证明副本由本操作产生的步骤保留两份正文，操作记录冲突、补偿任务转人工核对。进程中断不被解释成已成功，正文和数据库不一致也不能通过成功标签掩盖。

沿用现有用户级查询与重试入口：

- `/api/governance/operations`、`/{batchId}` 及 `/items`：归档、撤销步骤和失败码。
- `/{batchId}/compensations`：补偿状态、次数、建议及人工处理记录。
- `/{batchId}/retry`、`/{batchId}/rollback`、补偿重试：明确触发新的有界处理。
- `/api/file-operations/deletions`：物理删除的保留时间、状态、次数与固定错误码；`/{id}/retry` 在核对身份后重新排队。

逻辑删除和物理删除意图在同一数据库事务提交；实际正文删除在提交后执行。物理清理失败保留任务、退避或人工状态，不能清除失败记录冒充完成。正文发生变化时条件删除拒绝，原内容保留，显式身份核对/修复后才重试。

## 离线和强杀验收

完整后端回归及后续定向报告汇总为 **438 项，0 失败、0 错误、9 跳过**；跳过项为 7 个未启用的真实 MinIO 合同用例和 2 个本机无符号链接创建权限的用例。本轮实际 Windows junction、跨盘、解析子进程及本地治理均运行。服务端 Redis 回归使用临时无持久化实例；桌面场景仍不依赖该实例。

测试不关闭用户机器的网络适配器。隔离桌面 JVM 将 Redis/MinIO 指向不可达 loopback 端口，关闭可选 embedding/inbox；已确认治理操作仅依赖 H2、正文和持久化快照。预览合同测试使用固定本地模型响应夹具，仍读取真实文件，未向外部模型发送内容。

`DesktopGovernanceIntegrationTest` 使用真实桌面 H2、owner 五区域和本地适配器运行共享业务服务，覆盖：

1. 真实预览前后正文清单、SHA-256、完整正式字段/原标签不变。
2. 确认归档使用预览原路径，之后恢复名称、分类、摘要、标签状态/备注及正文；revision 正常递增。
3. 归档目标占用在确认时可见，撤销原路径占用进入冲突；已有正文均不覆盖。
4. 已撤销/正式状态改变后的过期清理不会删除当前正文，也不改写历史成功记录。
5. 物理删除指纹冲突产生 FAILED → MANUAL_REVIEW，状态可查询，核对原摘要并显式重试后完成。

`scripts/verify-local-governance.ps1` 复用独立 JVM 强杀探针，执行 14 个持久化边界：

- 归档：台账写入、源验证、复制未记账、目标记账、元数据提交、来源已删除。
- 撤销：请求台账、复制未记账、副本验证、元数据恢复、旧归档正文已删除。
- 删除：意图入队、任务 claim、正文已删除。

每个边界第一次 JVM 通过 Runtime.halt(73) 立即退出，第二次新 JVM 使用同一目录正常启动；对账后核对正文 SHA-256、正式快照、台账与冲突/成功状态。归档/撤销探针还真实执行 HTTP 登录、带 revision 的文件内容 API 读取，并确认匿名请求被拒绝。复制未记账两个边界明确验证冲突和 MANUAL_REVIEW，不能把等字节正文当成成功归属证明。

运行入口：

```powershell
./scripts/verify-local-governance.ps1 -JavaPath '<Java17+目录>/bin/java.exe' -MavenPath '<Maven目录>/bin/mvn.cmd' -KeepArtifacts
```

所有样本、H2、库标识、密钥和日志仅在被忽略的 `backend/.test-tmp/` 隔离目录。脚本不按进程名批量停止服务，不连接真实业务数据库或 MinIO bucket。

本轮 14 个强杀/重启边界均通过，恢复后的鉴权文件 API 返回原正文；同一套已有治理/撤销/补偿测试亦进行回归。该结果覆盖进程强杀和网络依赖不可达，不冒充 NAS 实机、硬件断电或 R35/R42 的完整备份恢复验收。
