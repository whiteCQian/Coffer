# R31｜本地安全导入

实现日期：2026-10-08。本轮沿用 R20 的存储端口/持久化意图和 R30 的桌面数据目录，新增 owner 工作区、受控收件箱、路径预览确认及文件库根目录重绑定检查。R30 的未提交改动一并保留，未修改真实账号或业务文件。

## owner 工作区

桌面文件库使用以下布局：

```text
<library>/
  .coffer-library.json        # R30 库 UUID/格式版本
  .coffer-library.lock        # 独立的文件库进程锁
  users/<ownerId>/
    .coffer-owner.json        # owner、库 UUID、工作区格式版本
    inbox/                   # 用户投入的原文件，导入后保留
    managed/files/...         # 正式入库文件
    managed/archive/...       # 用户确认后的归档位置
    work/                    # 外部编辑工作副本的受控区域
    quarantine/              # 隔离区
    lost-found/               # 人工核对区
```

owner 来自服务端身份与 TenantContext，不能从请求路径或 DTO 指定。首次使用创建空工作区并保存绑定标识；已有工作区必须保持标识和五个区域一致，缺失或链接替换时拒绝自动补造。数据库已有文件而整个 owner 目录消失时拒绝初始化替代空目录。

新桌面上传/导入和归档路径由 PathGenerator 生成到 `managed`。R30 的 `users/<owner>/files`、`archive` 旧正式对象保留读取与恢复兼容，不搬迁已登记的对象。旧 owner 目录只有在数据库已有对应用户文件、目录仅含这些已知历史区域时才进入受控布局升级；任意非空、未绑定目录拒绝初始化。

正式对象盘点只包含 `managed` 和兼容的旧 `files/archive`，不把收件箱原件、工作副本、隔离文件、lost-found 文件或 owner 标识当作孤儿正文。过期 staging 清理也限定在这些正式区域，不删除其他区域里恰好以 `.coffer-stage-` 开头的原文件。

## 空库初始化与根目录重绑定

- 沿用 `--coffer.desktop.initialize=true` 的明确首次初始化；数据目录和所选 library 都必须为空。写入前执行实际临时文件写入/force/读取/删除检查，不能通过修改 ACL 绕过原有不可写状态。非空、不可写、链接/连接点及不受控重叠目录均拒绝初始化，原内容保持。
- 可用 `--coffer.desktop.library-directory=<绝对路径>` 或 `COFFER_DESKTOP_LIBRARY_DIR` 指定独立正文根目录。默认仍为用户数据目录下的 `library`，不能位于当前安装目录中，也不能与数据库/日志等数据目录重叠。
- 首次初始化同时写入 library 标识和数据库绑定；正常启动持有数据目录锁和 library 锁。即使两个数据目录副本指向同一正文库，也不能同时写入该库。
- V39 增加数据库中的 `library_root`。R30 旧库升级时，仅对已通过 UUID/密钥校验的默认 library 保存初始绑定；不会自动采纳一个新指定的外部根目录。
- 更换正文路径必须先停用应用并由用户迁移完整原库，然后明确使用 `--coffer.desktop.rebind-library=true`。新库必须具有相同的安装 UUID、library UUID 和格式版本；新空目录或另一套库不能作为重绑定目标。
- 重绑定前检查上传意图、重命名、工作副本、物理删除、归档/撤销和 IMPORTING 收件箱记录，存在未完成步骤即拒绝。随后按页核对每个当前 owner 文件的大小与 SHA-256，成功后才更新 `library_root`。路径变更、UUID 冲突、正文缺失/损坏或未完成操作均有固定启动错误码。
- 根目录重绑定只更新已验证的配置绑定，不自动移动、改名或删除正文。后续启动必须继续指定新库路径。`requiredBackupEntries()` 同时包含外部库的实际根目录，R35 的一致性备份不能只复制数据目录而遗漏外部正文。

示例：

```powershell
# 仅首次：两个目标目录都必须为空
./scripts/start-desktop.ps1 -JavaPath '<Java17+目录>/bin/java.exe' -UserDataDir '<数据目录>' -LibraryDir '<独立正文目录>' -Initialize

# 迁移完整原库并停用旧进程后，明确核对并重绑定
./scripts/start-desktop.ps1 -JavaPath '<Java17+目录>/bin/java.exe' -UserDataDir '<原数据目录>' -LibraryDir '<迁移后正文目录>' -RebindLibrary
```

## 受控收件箱与确认流程

桌面收件箱默认启用，并固定为当前用户的 `users/<owner>/inbox`，任意 `COFFER_INBOX_DIRECTORY` 模板不能将其改为外部路径。服务端模式仍保留显式启用的 owner 模板，但 `{ownerId}` 必须是完整目录段，绝对路径不能包含 `.`/`..` 或多重/嵌入式占位符。

扫描只处理受控目录的直接普通文件，不递归读取子目录；每次检查整个目录链，拒绝符号链接、Windows junction、其他重解析目录以及其他 owner 的来源。快照键包含文件名、大小、mtime、文件身份和 SHA-256，避免大小/时间相同而内容不同的文件复用旧预览。超过 32MB 的文件在正文哈希之前停止，记录不支持状态。

稳定的桌面快照进入 `AWAITING_CONFIRMATION`，预先生成并持久化唯一目标路径。此时不创建正式文件或分析任务，也不要求自动导入模型授权。首页进度面板展示原文件名和完整目标；用户确认路径后，再通过既有模型端点授权提交。敏感/未知正文仍遵守 R25 的逐文件模型授权，不因本地路径确认而跳过内容发送边界。

`POST /api/inbox-imports/{id}/confirm` 只接收预览中的 `targetPath`，比较请求与数据库中的路径，并再次验证 owner、快照和目标区域。目标不允许在执行时重新分配、自动改名或覆盖；目标被占用时进入人工核对态。重复确认已完成记录保持幂等，并发确认通过持久化 claim 拒绝重复复制。`/{id}/retry` 将人工核对后的桌面记录恢复到待确认路径状态，仍需用户确认。

扫描采用按 owner 的轮转分页，并保持有界候选队列；保留原件后，已导入文件不会长期占据第一批扫描名额而阻止后续文件被发现。进度接口优先返回待确认记录，再补充最近结果，避免刚完成的 50 个文件遮蔽较早的待确认批次。lastScanAt 和扫描游标按 owner 分开。

外部文件可以由用户通过系统复制投入自己的 inbox，或通过既有浏览器文件选择/上传入口提交。后端不暴露接收任意宿主机绝对路径的公共接口；原生文件选择/拖放桥由 R34 桌面壳接入受控流程。

## 复制、校验与失败边界

`LocalImportSource` 以 NOFOLLOW 打开只读句柄并取得共享锁，核对大小、mtime 和文件身份，再用同一句柄计算 SHA-256。被占用、发生替换或变化、无法读取的文件停止导入，不删除来源。

本地 `writeVerified` 在目标目录的同卷 staging 中复制并检查大小及预览 SHA-256，执行 force 后才以 no-overwrite 的同卷原子发布方式提交正文；错误指纹或冲突不会发布替代文件。复制完成后再次核对来源，随后登记文件元数据和处理任务。事件只在数据库事务提交后触发。业务处理不把跨盘移动当作原子操作，也没有任何删除来源文件的步骤。

注册任务或事务失败时沿用 R20/R21 的持久化操作意图和人工恢复，不以临时日志冒充完成。API 失败时 UI 不显示导入成功；复制已完成但登记失败的对象保留在可核对的意图中，不能直接作为新任务重用。

另外修复 OwnerAuthorizationAspect 对 `Path` 的旧递归缺陷：Path 是自包含的 Iterable，不能按嵌套实体集合无限遍历。路径现在作为标量传给上述受控来源验证；owner 实体和显式 ownerId 的检查保持。
